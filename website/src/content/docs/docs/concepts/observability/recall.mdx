title: "Recall"
description: "The local history of every command: what ran, what it executed, and what it printed."
---

Recall records each `sqb` invocation in a local SQLite store, or in a shared
[ClickHouse store](#sharing-history-in-clickhouse), so you can ask what happened after the fact: which command ran, how it ended, which statements it executed and how long they took, and
exactly what it printed. Recall is on by default and needs no setup.

## An investigation, start to finish

The waffle shop example's `daily_revenue` model has an audit, `revenue_is_non_negative`, at warn
severity. One night the payments feed starts recording a refund as a negative payment. The unit tests
still pass, because they run on mocked data. The build finishes with a warning that nobody reads.

The next morning, ask when the audit started failing, and what each of those builds reported:

```bash
sqb recall query \
  "SELECT a.invocation_started_at AS run, a.outcome, a.violation_count, i.status, i.exit_code
   FROM audit_results a JOIN invocations i USING (invocation_id)
   WHERE a.audit_name = 'revenue_is_non_negative' ORDER BY run DESC LIMIT 3"
```

```
-[ RECORD 1 ]---------------------------+
run             | 2026-10-20T00:01:44.784683Z
outcome         | warn
violation_count | 1
status          | completed
exit_code       | 0

-[ RECORD 2 ]---------------------------+
run             | 2026-10-20T00:00:34.652468Z
outcome         | pass
violation_count | 0
status          | completed
exit_code       | 0

-[ RECORD 3 ]---------------------------+
run             | 2026-10-19T23:59:23.827831Z
outcome         | pass
violation_count | 0
status          | completed
exit_code       | 0

3 rows
```

The audit started warning on the latest build, and that build still exited 0, so nothing alerted.

See what that build printed, exactly as the scheduler saw it:

```bash
sqb recall output last --tail 4
```

```
  daily_revenue
    audit revenue_is_non_negative returned 1 row

✓ Completed with warnings  PASS=89  WARN=1  FAIL=0  INSUFFICIENT=0  SKIP=0  TOTAL=90  (3.08s)
```

Then check what is true in the warehouse now, with `sqb recall query` again:

```bash
sqb recall query --backend warehouse \
  "SELECT payment_id, order_id, amount_cents, paid_at FROM prod.stg_payments WHERE amount_cents < 0"
```

```
-[ RECORD 1 ]---------------------------+
payment_id   | 9
order_id     | 8
amount_cents | -2200
paid_at      | 2026-04-03 15:42:00

1 row
```

Payment 9 is a refund recorded as a negative payment, and it is still in prod. A coding agent can
follow the same steps: the history is SQL over the [views](#querying-history), and every query can
return `--json`.

## What is recorded

For every recorded invocation, Recall keeps:

- the invocation itself: command, arguments, target, adapter, status, exit code, and timing, and
  for a failed invocation its cause as `error_type`, `error_code` and a one-line
  `error_message`, also when the command reported the failure only through its exit code (for
  example `sqb debug` failing to connect records `ConnectionError` and `C980`);
- the commit it ran from (`git_revision`), see [Git revision](#git-revision);
- where it came from (`origin`) and, for an orchestrated run, the job and run that started it, see
  [Where a run came from](#where-a-run-came-from);
- its [lifecycle events](/docs/concepts/observability): runs, resource attempts, statements,
  retries, and audit results;
- the SQL text of every executed statement, stored once per distinct statement and shared across
  invocations;
- its stdout and stderr, byte for byte, in the order they were written, up to
  [`max_output_bytes`](#output-limit) of each stream;
- framework diagnostics at or above `diagnostics_min_severity`.

Writes happen on a background thread and never fail the command. A command that cannot record all
of its history still succeeds, prints a warning followed by its own final status, and
`output_invocations` reports the gap. An invocation whose process died without finishing has
status `abandoned`.

`sqb recall` only reads history: it publishes no lifecycle events, runs no project sinks, and keeps
no compute logs, so a query starts quickly. Every command is recorded except `sqb recall` itself, commands that create a project (such as
`sqb init`), and raw-query `sqb diff`. Commands `sqb` answers without starting Python are not
recorded either: a `sqb compile` answered from the launcher's warm cache, and `sqb clean`, `sqb skills`,
`sqb rules list` and `sqb rules show` in a project with no custom rules, rule options or sinks.

The store is `logs/recall.sqlite3` in the project directory. Add `logs/` to `.gitignore`; the store
can contain sensitive SQL and output.

## Git revision

`invocations.git_revision` is the commit `HEAD` names in the repository above the project
directory, including git worktrees and submodules, whose `.git` is a file pointing at the
repository. Deployments usually have no `.git` at all, so set the revision when building the image
or starting the job, or comparing production runs by `git_revision` finds nothing:

```bash
export SQLBUILD_GIT_REVISION="$(git rev-parse HEAD)"   # recorded as git_revision
export SQLBUILD_GIT_DIRTY=false                        # optional: recorded as git_dirty (true/false)
```

`SQLBUILD_GIT_REVISION` takes precedence over the repository. Without `SQLBUILD_GIT_DIRTY`,
`git_dirty` is `NULL`.

## Where a run came from

Every command is recorded in the store of the target it ran against, including a quick
`sqb debug --target prod --no-connection` on a laptop. Each invocation therefore says where it came
from, so a local check reads differently from a failed scheduled build:

- `origin` is `integration` when an integration such as Dagster started the command (it records
  `external_context`), `ci` when the command ran in CI, and `local` otherwise. CI is detected from
  the variables CI systems set: `CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `JENKINS_URL`,
  `CIRCLECI`, `TF_BUILD`, `TEAMCITY_VERSION`, `BITBUCKET_BUILD_NUMBER` and `CODEBUILD_BUILD_ID`
  (any value other than empty, `false` or `0`).
- `command_mode` says what a diagnostic command checked: `sqb debug` records `config_only` with
  `--no-connection` and `config_and_connection` otherwise. Recall never stores a command's raw
  arguments, which can hold secrets.
- `external_context` is the JSON object the integration supplied. The `invocations` view exposes
  its common fields as columns: `integration` (for example `dagster`), `integration_job`,
  `integration_run_id` and `integration_retry`. The Dagster integration also records `step_key`
  and `partition_key`, which you read from `external_context` with the store's JSON functions.

## Settings

Configure Recall in `[recall]` in `sqlbuild_project.toml`. A `[targets.<name>.recall]` table
overrides individual keys for one target.

```toml
[recall]
retention = "30d"             # days of history to keep; also accepts hours, such as "720h"
shutdown_timeout = "3s"       # longest delay Recall may add when a command exits
diagnostics_min_severity = "info"
max_output_bytes = 2097152    # bytes of each output stream to keep; 0 keeps everything

[targets.ci.recall]
enabled = false               # do not record runs against the ci target
```

| Key | Default | Description |
|-----|---------|-------------|
| `enabled` | `true` | Set to `false` to stop recording |
| `write_connection` | (none) | The connection every command writes its history to: a `sqlite` connection whose `path` names the store, or a `clickhouse` connection. Requires `read_connection` in the merged settings: `[recall]`, the target's table or `sqlbuild_local.toml` may set either. Defaults to `logs/recall.sqlite3` |
| `read_connection` | (none) | The connection `sqb recall query`, `schema` and `output` read; may name the same connection as `write_connection`. Set alone to read shared history while this machine's own commands record to `logs/recall.sqlite3` |
| `retention` | `"30d"` | How long invocations are kept, in days (`d`) or hours (`h`), up to 3650 days |
| `shutdown_timeout` | `"3s"` | The cap on time spent flushing history at exit, in `s` or `ms`, up to 10 minutes |
| `diagnostics_min_severity` | `"info"` | `trace`, `debug`, `info`, `warning`, `error`, or `critical` |
| `max_output_bytes` | `2097152` for the local store | Bytes of stdout and of stderr kept per invocation, an integer; `0` keeps everything. See [Output limit](#output-limit) |

To turn Recall off for the whole project:

```toml
[recall]
enabled = false
```

Recall never delays the start of a command. At exit it waits at most `shutdown_timeout` for queued
history to reach the store; anything left is counted as dropped. A second Ctrl-C stops waiting at
once.

## Output limit

Recall keeps at most `max_output_bytes` of each output stream per invocation: the first half and
the last half, byte for byte. The local SQLite store defaults to 2 MiB, so a command that prints
more keeps its first and last MiB of stdout and of stderr. Set `max_output_bytes = 0` to keep
everything, or a larger number to keep more; a `[targets.<name>.recall]` table can set it for one
target. The command itself prints nothing about the limit.

The middle that was left out is one gap: `output_invocations` reports `gap_reason = 'truncated'`,
the left-out byte count in `truncated_bytes`, and `complete = 0`. `sqb recall output` prints a
note in its place:

```
… 23.6 MB of stdout not recorded (kept the first and last 1 MiB). Raise [recall] max_output_bytes to keep more.
```

The end of a stream is held in memory until the command exits, so a process that is killed keeps
only the first half.

## Retention

Commands occasionally prune invocations older than `retention`, with all of their events, output,
and diagnostics. SQL text is removed once no remaining invocation references it. Pruning runs in
the background within the exit budget and never removes an invocation that is still running.

## When the store cannot be written

If the store location is not writable, the command still runs and prints a notice on stderr with
the SQL an administrator can use to create the store; the notice comes before the command's own
output whenever the problem is visible from file permissions. The notice
repeats at most once a day. If the store file is not a SQLite database, Recall moves it aside to
`recall.sqlite3.corrupt-<UTC timestamp>`, starts a fresh store, and says so once. Commands that
find the same corrupt file coordinate through `recall.sqlite3.lock`, so only one of them moves it.

A `write_connection` on any adapter other than `sqlite` or `clickhouse` is not supported; Recall
prints a notice and records nothing.

## Sharing history in ClickHouse

Point `write_connection` and `read_connection` at ClickHouse connections to keep one history for a
whole team. Every machine
that writes to it, including CI and scheduled production runs, becomes queryable from anywhere:
see what last night's production build ran and printed without access to the machine, find the
first run where an audit started failing across everyone's runs, or compare a production run with
your own by `target`, `git_revision` or `sqlbuild_version`.

The connection needs `adapter = "clickhouse"` when the project uses another adapter. Recall creates
and upgrades its own store on the first write: the `database` when it does not exist yet, then its
tables, views and schema version. A writer that may run that DDL needs no other setup.

```toml
[connections.history_writer]
adapter = "clickhouse"
host = "${env:CLICKHOUSE_HOST}"
user = "recall_writer"
password = "${env:RECALL_WRITER_PASSWORD}"
database = "observability"

[connections.history_reader]
adapter = "clickhouse"
host = "${env:CLICKHOUSE_HOST}"
user = "recall_reader"
password = "${env:RECALL_READER_PASSWORD}"
database = "observability"

[recall]
write_connection = "history_writer"  # every command writes history; creates the store on first use
read_connection = "history_reader"   # sqb recall query, schema and output (SELECT only)
retention = "30d"
```

`sqb recall query`, `schema` and `output` use only `read_connection` and never create or change
anything in the store, so someone investigating production runs needs no credentials that could
rewrite or delete its history. Both keys may name one connection when separate users are not
wanted. A machine that only reads shared history, such as a laptop investigating production runs,
sets only `read_connection`; its own commands keep recording to the local store. Each side
resolves only its own connection, so environment references in the other connection, such as the
writer's password on a reader's laptop, need not be set.

### Users and grants

SQLBuild doesn't enforce grants; it lets you separate the roles. Give the writer the rights to
create and upgrade the store in its database, so the first command sets it up and later SQLBuild
versions upgrade it without anyone running DDL by hand:

```sql
-- once, as an administrator: the users
CREATE USER recall_writer IDENTIFIED BY '...';
CREATE USER recall_reader IDENTIFIED BY '...';
GRANT CREATE DATABASE, CREATE TABLE, CREATE VIEW, DROP TABLE, ALTER ADD COLUMN, SELECT, INSERT
  ON observability.* TO recall_writer;
GRANT SELECT ON observability.* TO recall_reader;
```

`DROP TABLE` is needed because ClickHouse replaces a view through a temporary table; Recall never
drops a table itself.

| User | Rights | What happens |
|------|--------|--------------|
| Writer with the grants above | Create and upgrade the store | The first command creates the store; later versions upgrade it |
| Writer with only `SELECT` and `INSERT` | Write history | Works once the store exists. A missing or older store makes Recall print the statements an administrator should run |
| Reader with `SELECT` | Read history | `sqb recall query`, `schema` and `output` work, and can't change the store |

A reader may be a standard read-only user (`SETTINGS readonly = 1`, or a settings profile with
it). Its queries run with the server's own settings; every other reader gets the
[settings SQLBuild pins](/docs/concepts/adapters/clickhouse#settings-sqlbuild-pins). The views
return the same rows either way. `sqb recall query` runs with `readonly = 2`, which refuses writes
but allows query settings, unless the user is already read-only. A user that may not set the row
limit gets the same truncated result, cut off while reading. A setting Recall needs that the user
may not change fails with an error naming it: set it in the user's profile, or give the user
`readonly = 2`, which keeps it read-only.

### Setting up and upgrading the store

- **Setup.** On first use, the writer creates the database if it's missing, printing
  ``Recall: created ClickHouse database `observability` for the store.`` once, then the store's
  tables and views. An existing database is used as it is, whatever its engine.
- **Clusters.** The database is created on the server the writer connects to, never `ON CLUSTER`.
  On a self-managed cluster whose default database engine isn't `Replicated`, create the database
  yourself first with `ENGINE = Replicated(...)`; Recall leaves it alone. ClickHouse Cloud needs
  nothing. `ON CLUSTER` stores aren't supported: use a single ClickHouse server or ClickHouse Cloud.
- **Without DDL rights.** If the writer may not create or upgrade the store, the command still
  runs and exits as it otherwise would. Recall prints the statements an administrator should run, at
  most once a day, starting with `CREATE DATABASE IF NOT EXISTS` when the database is missing.
  `sqb recall schema --ddl` prints them again. A store behind the current version still receives
  history, in the columns that exist.
- **Mixed versions.** A writer never replaces the views of a store that a newer SQLBuild version
  created.
- **Many writers.** Many concurrent commands can write one store. A repeated delivery is counted
  once. A record written again with different content keeps the stored row, and the rejected copy
  is listed in the `conflicts` view.
- **Writes.** History is sent about every five seconds and when the command ends, with the same shutdown
  budget and exit-code guarantees as the local store.

### Retention in ClickHouse

Retention belongs to the store. Every table has a TTL of `retention`; SQL text is kept a week
longer, and for as long as a kept invocation references it. The views hide expired rows at once,
but ClickHouse drops expired parts in the background, so rows may stay on disk for a while.

When a project's `retention` differs from the tables' TTL, Recall warns once a day with the
`ALTER TABLE … MODIFY TTL` and view statements that would apply it. It never changes the TTL
itself.

### Reading a ClickHouse store

`sqb recall query`, `schema` and `output` read the ClickHouse store, so queries use ClickHouse SQL.
`--json` output includes the server's `rows_read`, `bytes_read` and `query_id`.

## Filtering what Recall stores

By default Recall stores every lifecycle event and every output byte. To decide yourself, write a
[sink](/docs/concepts/observability/sinks) with a parameter annotated `RecallWriter`: it replaces
Recall's default for its stream, and Recall stores only what it publishes.

```python
from sqlbuild.recall import RecallWriter
from sqlbuild.sinks import CommandOutputRecord, command_output_sink


@command_output_sink
def recall_output(record: CommandOutputRecord, writer: RecallWriter) -> None:
    redacted: bytes = record.data.replace(b"secret-token", b"[redacted]")
    writer.publish_command_output(record.replace(data=redacted))
```

- A `@command_output_sink` replacement receives each output chunk with its exact bytes in
  `record.data` (record schema version 2). `record.replace(data=…, message=…)` returns a copy that
  keeps the record ID and sequence; publish at most one record per call.
- A `@lifecycle_event_sink` replacement receives each event its `event_kinds` and `min_severity`
  accept and keeps it with `writer.publish_lifecycle(event)`.
- Both replacements run on Recall's background thread, so a slow one never delays the command or
  other sinks by more than `shutdown_timeout`; what it has not handled by then is counted as
  `dropped`. Output written before discovery finishes is held until the replacement can see it.
- A record the sink does not publish is counted as `filtered`; a sink that raises an exception has
  its record counted as `failed`, and Recall never falls back to storing the unfiltered record. The
  command's exit code and output are unaffected. `output_invocations.filter_active` is `1` for invocations
  that ran a replacement.
- There is at most one replacement per stream; discovery fails with `D015` naming each
  `path:function` otherwise. A replacement takes only its record and the writer, not providers, and
  the provider name `recall_writer` is reserved.
- Other sinks keep receiving every record. With `enabled = false`, no replacement runs.

## Querying history

Use [`sqb recall`](/docs/cli/recall) to read the store: `sqb recall query` for questions and
`sqb recall output` for what a command printed. The views fold the raw `recall_*` tables for you
(duplicate deliveries, terminal facts, retention), so start there; query the store's database
directly only for something the views do not expose. Queries are read-only `SELECT` statements,
in the store's SQL dialect, against these views:

| View | One row per |
|------|-------------|
| `invocations` | Invocation, with status, exit code, and timing |
| `statements` | Executed statement, with resource, kind, purpose, duration, and row counts |
| `audit_results` | Evaluated audit |
| `events` | Lifecycle event |
| `diagnostics` | Retained diagnostic |
| `artifacts` | Reference from an invocation to captured SQL, with its text |
| `output_invocations` | Invocation's output, with completeness |
| `output_transcripts` | Invocation's stdout, stderr, and combined output |
| `output_tail` | Recent output chunk |
| `conflicts` | Record written twice with different content |

Output shows an invocation ID by its first eight characters, such as `38ecc95e`. Any unique prefix
names the invocation: `sqb recall output 38ecc95e` works, and a prefix that matches more than one
invocation fails and lists the matches. In SQL, match a prefix with
`invocation_id LIKE '38ecc95e%'` on SQLite or `startsWith(invocation_id, '38ecc95e')` on ClickHouse.

Run `sqb recall schema` for every column, and check the values a column holds before filtering on
it, for example `SELECT DISTINCT resource_kind, purpose FROM statements`: a model's
`resource_kind` is its materialization, such as `table` or `view`, and its build statements have
`purpose = 'model_build'`.

Every view has `invocation_id` and `invocation_started_at`. Filter on them to keep a query cheap:
on a ClickHouse store, a filter on either reaches the table reads, so a query about one invocation or
the last day reads that part of the store instead of folding the whole retention window.

### Common questions

These run as written on the local SQLite store and on a ClickHouse store.

The latest runs of an orchestrated job, by the job name its integration records:

```bash
sqb recall query "SELECT invocation_id, invocation_started_at, status, duration_ms,
    integration_run_id, integration_retry
  FROM invocations WHERE integration_job = 'orders_job'
  ORDER BY invocation_started_at DESC LIMIT 5"
```

The latest scheduled and CI builds, leaving out local diagnostics such as `sqb debug`:

```bash
sqb recall query "SELECT invocation_id, invocation_started_at, command, origin, status
  FROM invocations
  WHERE command IN ('build', 'run', 'test', 'audit', 'seed') AND origin IN ('integration', 'ci')
  ORDER BY invocation_started_at DESC LIMIT 10"
```

The slowest models in a run:

```bash
sqb recall query "SELECT resource_name, resource_kind, sum(duration_ms) AS total_ms
  FROM statements WHERE invocation_id = '<invocation_id>' AND purpose = 'model_build'
  GROUP BY resource_name, resource_kind ORDER BY total_ms DESC LIMIT 10"
```

Audits that did not pass:

```bash
sqb recall query "SELECT invocation_started_at, audit_name, outcome, violation_count, execution_error
  FROM audit_results WHERE outcome <> 'pass'
  ORDER BY invocation_started_at DESC LIMIT 20"
```

What a run printed at the end:

```bash
sqb recall output <invocation_id> --tail 50
```

### From a statement to the warehouse

`statements.query_id` is the warehouse's own ID for the statement on Snowflake (the query ID) and
ClickHouse (the `query_id` in `system.query_log`). Look it up in the warehouse's query history to
see what Recall does not record, such as the warehouse size, queueing and spilling behind a slow
statement. It is `NULL` on DuckDB and BigQuery; a BigQuery statement's job ID is in its
`statement_submitted` event instead, as `payload` field `job_id` in `events`.

## Relationship to compute logs

Compute logs (`logs/<date>/<invocation_id>/stdout.log`, `stderr.log`, and `diagnostics.jsonl`) are
written alongside Recall. Recall stores the same output bytes, captured at the same point, so
`sqb recall output` matches the compute log files.
